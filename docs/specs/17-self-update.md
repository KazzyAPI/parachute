# 17 Self-update

**Status:** Accepted

Parachute updating its own container with a side-by-side handover. `internal/handover` holds the marker format and `graph.SelfRunner` is the seam where the transaction plugs in.

### UPD-018 Self-update
A **self-update** is an update of Parachute's **own container**: the container this instance runs in, as identified by the engine ([ADR-0016](../adr/0016-identifying-own-container.md)); a Parachute that is not containerised has no own container and never self-updates. Parachute never needs a `parachute.self` label to find it, and the label never makes a container this instance's own (SEL-012); another Parachute container is never changed by this instance. The design is [ADR-0014](../adr/0014-self-update-safety.md). Before its `handover` phase a self-update MUST follow these rules:

- **Approval.** It is always held with reason `approval_required` until its approved digest (UPD-020) is approved (API-007), as the glossary's **Self-update approval** says; no profile, flag, or label removes this hold.
- **Order and scope.** It runs after every other stack in the cycle, as a transaction of the own container alone, even when that container belongs to a Compose project; no other container is stopped or joined to it (DEP-003).
- **Image.** It pulls by the approved digest, checks it, and re-tags it as UPD-020 says; a mismatch gives `failed` with reason `pull_failed`.
- **Snapshot.** The own container's effective backup mode is always `none`, whatever its labels or `--backup`: its configuration is recorded, no data is copied, and it is never stopped (BKP-003's `stop` mode does not apply). VER-009 never restores data for it, because the new instance writes nothing in the state directory before it owns the state file.
- **Configuration.** Besides UPD-007, an own container that publishes a host port or has a static IP address on any network fails with reason `config_unreproducible` naming the field, because the replacement must run beside it.

The `handover` phase (state `handover`, [glossary: Transaction state machine](glossary.md#transaction-state-machine)): the old instance owns the state file ([ADR-0008](../adr/0008-state-storage.md)) and runs the whole transaction.

1. The old instance records state `handover` in the state file, then writes the **handover marker** `<state-dir>/handover.json` (by replacing, never in place) with `format` `parachute.handover/v1`, the transaction ID, the old container's ID, and the approved digest. Then it renames its own container (UPD-008) but keeps it running, and creates and starts the replacement (with the UPD-005 labels).
2. An instance that starts while a marker exists MUST first validate it ([glossary: Trust boundaries](glossary.md#trust-boundaries)): it parses as `parachute.handover/v1` with a transaction ID matching UPD-002 and a 64-hex container ID, and either the marker's container ID is the starting instance's own container ID, or the starting instance's own container carries `parachute.transaction` equal to the marker's transaction ID and runs an image whose repository digests contain the marker's digest. Otherwise it MUST exit with code 2 naming `handover.json` and leave the file unchanged. An instance whose own container is not the one the marker names is in **handover mode**: it MUST NOT read or write `state.json`, resolve open transactions (UPD-016), run cycles, or change any container, and it MUST log at `info` that it is waiting for handover with the transaction ID. Its other startup checks complete normally, so `parachute healthcheck` (DMN-006) passes.
3. The old instance verifies the replacement (VER-001). On success it records the cycle's results and the transaction as `committed` in the state file, sends the cycle report, removes the marker, and from then on MUST NOT read or write the state file, run cycles, or change any container. When the marker is gone, the new instance reads the state file; if it records the marker's transaction as `committed`, the new instance owns the state file, removes the old container if, and only if, it has the container ID the marker named and is named `<name>-parachute-<suffix>` for that transaction (UPD-017), applies `--cleanup` (UPD-010), and starts its cycles.
4. If the replacement fails verification, the ceiling is reached (UPD-019), or an engine write fails (DMN-005), the old instance MUST roll back (state `rolling_back`): remove the replacement, rename its container back, record `rolled_back` with the VER, UPD-019, or DMN-005 reason and the POL-010 hold for that digest, remove the marker, keep running, and report the result `rolled_back` at `warn`.
5. The result MUST be `rollback_failed` with reason `restore_failed` (an `error` notification, NTF-012) only when the old instance cannot remove the replacement or rename its container back, or two Parachute containers for that scope are left running. The old instance keeps the state file.
6. If, while the marker exists, the old container no longer exists or is neither running nor restarting, the new instance in handover mode MUST take ownership of the state file and first read the transaction's recorded state. If it is `committed` (the old instance stopped after the commit point and before removing the marker), the new instance MUST remove the marker and continue as in step 3: it removes the old container under the same checks, applies `--cleanup`, and starts its cycles; the result stays `updated`. Only if the recorded state is open (`handover` or `rolling_back`) MUST it record the transaction as `rollback_failed` with reason `interrupted`, remove the marker, send the `error` notification (NTF-012), and change no container. If instead the marker names the starting instance's own container (the old instance restarted), that instance owns the state file and also first reads the recorded state: if it is `committed`, the instance is superseded: it removes the marker and exits with code 2 (below), changing nothing else, and the new instance continues as in step 3; if it is open, it resolves the transaction by rollback as in step 4, with reason `interrupted`. A recorded terminal state is never changed (UPD-009, glossary); for a terminal state other than `committed`, the instance only removes the marker.

When it records a self-update as `committed`, or `rollback_failed` with reason `interrupted`, the owner of the state file MUST add the old container's ID to the state file's `superseded_instances` list (CFG-010), in the same replacement of `state.json` that records the `committed` or `rollback_failed` state. That list is separate from `last_transaction`: a later transaction of the same stack never removes an entry. An entry MUST NOT be removed while the engine still has that container, and SHOULD be removed once it does not ([ADR-0008](../adr/0008-state-storage.md) Amendment). An instance whose own container ID is in `superseded_instances` MUST exit at startup with code 2, so a superseded instance never runs beside its successor. At the end of every self-update exactly one Parachute container for that scope is running, except after step 5. A self-update that ends `rollback_failed` (steps 5 and 6) freezes only the own container, never the rest of its Compose project ([glossary: Transaction state machine](glossary.md#transaction-state-machine), POL-010); `POST /v1/approve` naming the own container releases it, even when no update is held for it and the instance running as the own container is not the old container the transaction recorded (API-007).

- **Given** an armed Parachute with `--profile convenient`, `--protect-databases=false`, and `parachute.approval=auto` on its own container, and a newer Parachute image **When** a cycle runs **Then** the result for its own container is `held` with reason `approval_required` and no container is changed.
- **Given** an approved newer Parachute image and one other container with an update **When** a cycle runs **Then** the other container's `commit` line precedes the self-update's `snapshot` line, and afterwards exactly one Parachute container in that scope is running, with the original name, on an image whose repository digests contain the approved digest; no container named `<name>-parachute-<suffix>` for the transaction exists; `handover.json` does not exist; and `parachute status --json` shows `last_transaction.state` `committed`.
- **Given** an approved new Parachute image whose health check always fails **When** a cycle runs **Then** the original Parachute container is still running with its original ID and name, the replacement no longer exists, the result for it is `rolled_back` with reason `verify_failed` in a `warn` entry, no `error` notification is sent, and the next cycle holds that digest with reason `previous_attempt_failed`.
- **Given** an approved self-update in its `handover` phase, with old and new instance running side by side (the new image's health check passes after 30 seconds) **When** the test reads `state.json`, `handover.json`, and the new instance's log during verification **Then** `state.json` records the transaction with state `handover`, `handover.json` names the transaction ID and the old container's ID, the new instance has logged that it is waiting for handover and no phase line, and the transaction later ends `updated` with the marker removed.
- **Given** the same, the old container with restart policy `no`, and the test running `docker kill` on the old container during verification **When** 60 seconds have passed **Then** the new instance is running, `handover.json` does not exist, `parachute status --json` shows the transaction as `rollback_failed` with reason `interrupted`, the webhook received an `error` notification with the transaction ID, the killed container still exists, and `parachute status --json` shows one `frozen` entry with that transaction ID whose `containers` lists only the own container.
- **Given** the same, and then `POST /v1/approve?container=<own container's name>` while the new instance already runs the approved digest (no update is held for it, and its container ID differs from the old container's ID recorded in the transaction) **When** the call returns **Then** the response is 200 with that transaction ID, and `parachute status --json` shows `frozen` as `[]`.
- **Given** an approved self-update, the old container with restart policy `no`, and a webhook that accepts the connection for the cycle report but does not answer **When** the test runs `docker kill` on the old container after `state.json` records the transaction as `committed` and while the report request is still open (so `handover.json` still exists) **Then** within 60 seconds `handover.json` does not exist, exactly one Parachute container in that scope is running (the new instance, on the approved digest), no container named `<name>-parachute-<suffix>` for the transaction exists, `parachute status --json` shows `last_transaction.state` `committed` with result `updated` and `frozen` as `[]`, and no `error` notification is sent.
- **Given** an approved self-update in its `handover` phase (the new image's health check passes after 30 seconds), the test running `docker pause` on the new instance and then `docker restart` on the old container **When** 60 seconds have passed **Then** the old container is running under its original name and ID, the replacement no longer exists, `handover.json` does not exist, `parachute status --json` shows the transaction as `rolled_back` with reason `interrupted` and `frozen` as `[]`, and no `error` notification is sent.
- **Given** Parachute's own container and `web` in Compose project `ops`, an approved self-update T1 whose old container (restart policy `no`) the test stopped with `docker kill` during verification, so T1 ended `rollback_failed` with reason `interrupted`, and then an ordinary transaction T2 for `web` that ended `updated` **When** the test runs `docker start` on the killed old container **Then** its Parachute process exits with code 2, and afterwards exactly one Parachute container in that scope is running, the successor.
- **Given** a `handover.json` written by the test that names a transaction ID and container ID unrelated to the starting instance **When** Parachute starts **Then** it exits with code 2, the message names `handover.json`, and the file's checksum is unchanged.
- **Given** an own container that publishes port `8080:8080` and an approved newer Parachute image **When** a cycle runs **Then** the result is `failed` with reason `config_unreproducible` naming the port, and the container keeps its ID.
- **Given** an approved self-update, the test running `docker pause` on the new instance at its `health_status: healthy` event, and then, once `handover.json` is gone, `docker stop` on the old container **When** the test starts the old container again **Then** its Parachute process exits with code 2.
